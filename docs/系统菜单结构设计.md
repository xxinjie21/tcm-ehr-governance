# 中医电子病历质控与标准化系统 \- 系统菜单结构设计文档

## 一、菜单结构总览

|一级菜单|承载功能范围|对应功能编号|
|---|---|---|
|首页|系统落地页，全局数据统计看板|拓展 2-4|
|病历管理|病历文件导入、单条新增、查看、维护、多条件检索|必做 3、必做 4、必做 5、查询 1|
|结构化解析|NLP 中医实体自动抽取全能力|必做 6-9|
|质控管理|多层数据校验、自动评分、辨证逻辑校验|必做 11/12、必做 15、拓展 1|
|人工复核|结构化手动校正、异常病历工单复核（两态流转）|必做 13|
|数据治理|数据清洗规整、标准化数据集导出|必做 14|
|词典管理|术语自动归一、国标术语库后台维护|必做 10、必做 16|
|系统管理|登录鉴权（按角色返回菜单）、操作日志（文件持久化）|必做 1、必做 2|

## 二、各菜单功能详细设计

### 1\. 首页

> 说明：登录默认落地页，仅做数据概览展示，不新增业务处理需求，全部复用拓展统计功能
> 
> 

#### 拓展 2-4 数据统计

**功能描述**：对已标准化病历批量统计各类统计指标，支撑首页数据看板

- 输入数据流：统计类型 type（symptom 症状频次 / syndrome 证型分布 / prescription 方剂中药频次）\+ 批量病历 ID 数组

- 输出数据流：按统计类型返回对应统计列表（症状频次、证型分布、方剂/中药频次）

- 接口设计

```http
POST /api/stats
请求体：{"type": "symptom", "recordIds": ["id1", "id2"]}
响应体（type=symptom）：{"statistics": [{"symptom": "发热", "count": 120}, ...]}
响应体（type=syndrome）：{"distribution": [{"syndrome": "风寒感冒", "count": 50}, ...]}
响应体（type=prescription）：{"formulaStats": [...], "herbStats": [...]}
```

### 2\. 病历管理

> 说明：全系统数据源头入口，覆盖病历入库、全生命周期维护，对应需求文档 3\.1 病历数据管理模块
> 
> 

#### 必做 3 病历批量导入与单条新增

**功能描述**：支持批量文件上传 + 手动单条录入双模式；自动校验文件格式、字段完整性，过滤空文件、格式错误文件

- 约束：单文件≤50MB，单次最多上传 20 个文件；支持 Excel(.xlsx) 格式

- 输入数据流：病历Excel文件（21个字段：登记号、门诊号、性别、年龄、就诊次数、西医诊断、中医诊断、现病史、自诉、主诉、望诊、脉诊、舌诊、查体、辨证结论、草药、随访、治疗效果、开单科室、医生工号、接诊时间）

- 输出数据流：导入任务 ID、导入结果摘要、带完整字段的入库病历

- 接口设计

```http
# 批量文件导入
POST /api/records/import
请求体：multipart/form-data 上传Excel文件列表
响应体：{"taskId": "string", "summary": {"total": 10, "success": 8, "failed": 2, "failures": [...]}}
# 查询导入任务进度（处理中/已完成；状态存于内存，服务重启后丢失，可重新发起导入）
GET /api/records/import/{taskId}/status
# 单条手动新增病历（21个字段）
POST /api/records
请求体：{"registrationNo": "...", "outpatientNo": "...", "gender": "...", ...}
```

#### 必做 4 原始病历查看

**功能描述**：病历数据只读锁定，禁止篡改，保障数据源真实可追溯

- 输入数据流：病历唯一 ID `recordId`

- 输出数据流：完整的21个字段信息（登记号、门诊号、性别、年龄、就诊次数、西医诊断、中医诊断、现病史、自诉、主诉、望诊、脉诊、舌诊、查体、辨证结论、草药、随访、治疗效果、开单科室、医生工号、接诊时间）

- 接口设计

```http
GET /api/records/raw/{recordId}
响应体：{"id": "string", "registrationNo": "string", "outpatientNo": "string", "gender": "string", ...}
```

#### 必做 5 病历修改、删除、标签与归档管理

**功能描述**：修改病历元数据（含分类标签、归档状态）、批量删除；原始文本不可修改，单条新增统一归入必做 3 导入接口

- 输入数据流：病历 ID、待更新字段（含标签、归档状态）、批量删除 ID 数组

- 输出数据流：操作成功 / 失败状态

- 接口设计

```http
# 修改病历结构化数据（21个原始字段只读，不可修改）
PUT /api/records/{recordId}
请求体：{"structuredData": {"symptoms": [...], "tongueList": [...], ...}}
# 批量删除病历
DELETE /api/records
请求体：{"ids": ["id1", "id2"]}
```

#### 查询 1 多条件病历查询

**功能描述**：多维度组合检索病历，支持分页、总数统计

- 输入数据流：患者 ID、就诊时间区间、科室、证型、症状关键词、病历状态（status，如 invalid）等筛选条件

- 输出数据流：符合条件病历摘要列表、数据总条数

- 接口设计

```http
POST /api/records/search
请求体：{"registrationNo": "...", "outpatientNo": "...", "gender": "...", "department": "...", "dateRange": ["2024-01-01", "2024-12-31"], "syndrome": "...", "status": "..."}
响应体：{"total": 100, "records": [{"id": "...", "registrationNo": "...", "outpatientNo": "...", ...}, ...]}
```

### 3\. 结构化解析

> 说明：NLP 核心转换模块，将自由文本转为机器可读实体，对应需求文档 3\.2 智能结构化解析模块
> 
> 

#### 必做 6-9 NLP 实体抽取

**功能描述**：NLP 统一抽取入口，一次从病历文本中抽取症状、舌象脉象、证型病因治法、方剂中药及剂量全部实体，输出完整结构化数据（structuredData）

- 输入数据流：病历原始自由文本

- 输出数据流：完整结构化数据（症状、舌脉、证型/病因/治法、方剂/中药+剂量，详见设计文档附录A）

- 接口设计

```http
POST /api/nlp/extract
请求体：{"text": "string"}
响应体：{"symptoms": [...], "tongueList": [...], "pulseList": [...], "syndromeList": [...], "causeList": [...], "treatmentList": [...], "formulaList": [...], "herbs": [...]}
```

### 4\. 质控管理

> 说明：三层全链路质量校验、自动评分、数据分级路由，对应需求文档 3\.3 多层智能质量控制模块
> 
> 

#### 必做 11-12 质控检查（缺失/格式/查重）

**功能描述**：事前质控统一检查：①缺失字段检查——校验脉象 / 舌象 / 证型 / 治法 / 方剂 / 中药六大核心必填项，标记缺失字段；②重复和格式检查——查重病历、校验字段格式合法性，标记格式异常项。统一接口 POST /api/qc/check 一次返回全部结果

- 输入数据流：完整结构化病历数据

- 输出数据流：缺失字段列表、是否重复布尔值、格式错误明细

- 接口设计

```http
POST /api/qc/check
请求体：{"structuredData": {...}}
响应体：{"missingFields": [...], "formatErrors": [...], "isDuplicate": false}
```

#### 必做 15 终末质控评分与质控报告

**功能描述**

1. 满分 100 分自动扣分规则（规则写死在代码 calculateScore）：核心字段缺失每项 \- 15 分、辨证逻辑冲突每项 \- 10 分、普通格式 / 重复每项 \- 5 分；

2. 分级路由：评分≥90 分且无逻辑错误→合格流入治理；60~89 分→自动进入人工复核（待复核列表）；＜60 分→标记无效数据（status=invalid，异常数据区，禁止导出）；

3. 严重问题判定：核心必填字段缺失≥3 项、证型 - 治法与证型 - 方剂规则同时冲突、文本无法解析 → 直接判定为无效数据（status=invalid），禁止导出；

4. 质控报告：页面展示评分与扣分原因文字，不生成独立报告文件 / 模块。

- 输入数据流：结构化病历、缺失 / 重复 / 格式 / 逻辑校验结果

- 输出数据流：病历得分、分级标识（合格 / 待复核 / 无效）、扣分明细、扣分原因文字

- 接口设计

```http
POST /api/qc/score
请求体：{"structuredData": {...}, "qcResults": {...}}
响应体：{"score": 82, "grade": "待复核", "deductions": [{"type": "missing_field", "points": 15}]}
```

#### 拓展 1 诊疗逻辑一致性检查

**功能描述**：事中核心质控规则，校验「证型 \- 治法、证型 \- 方剂、证型 \- 中药」匹配关系，规则写死在代码 checkLogic，固定 2-3 条核心规则（如：风寒感冒需配辛温解表、舌红不配脉沉迟），不支持自定义编辑

- 输入数据流：结构化证型、治法、方剂、中药数据

- 输出数据流：是否一致、冲突明细文本

- 接口设计

```http
POST /api/qc/check/logic
请求体：{"syndrome": "...", "treatment": "...", "formula": "..."}
响应体：{"consistent": false, "conflicts": ["证型与治法不符"]}
```

### 5\. 人工复核

> 说明：统一人工校正工作台，覆盖结构化前置修正、质控异常工单复核，修正后自动回流重质控，对应需求 3\.2、3\.3 闭环流程
> 
> 

#### 必做 13 结构化结果人工校正与异常复核

**功能描述** 病历状态二元化（待复核 / 已完成）：

1. 自动触发：评分<60 分标记无效数据；60≤评分<90 分或逻辑校验不通过 → 病历自动进入待复核列表；

2. 复核操作：审核人员查看高亮扣分项与逻辑错误，修改数据后点击「复核通过」；

3. 流程终结：系统自动重新评分与逻辑校验，通过则置为已完成，仍有错则保持待复核；

4. 超时处理：任务超过复核截止时间（deadlineTime）后仍保留在待复核列表，前端高亮提醒，系统不自动关闭或转交，由审核人员人工处理。

- 输入数据流：原始结构化数据、人工修正内容、待复核工单列表

- 输出数据流：更新后的结构化数据、工单状态（待复核 / 已完成）

- 接口设计

```http
# 获取待复核工单列表（60≤score<90 或 logicErrors 非空 自动进入）
GET /api/review/tasks
# 人工校正 + 复核通过（自动重算评分与逻辑校验，通过置已完成，否则保持待复核）
POST /api/records/{recordId}/review
```

### 6\. 数据治理

> 说明：数据标准化加工、成果数据集导出，系统最终输出层，对应需求文档 3\.4 数据治理与数据集导出模块
> 
> 

#### 必做 14 数据清洗、规整与标准数据集导出

**功能描述**

1. 自动清洗：去重、清除乱码、修补轻度缺失字段；

2. 数据规整：统一全病历字段格式，合并冗余内容；

3. 脏数据隔离：无效数据单独归档，不混入标准数据集；

4. 权限管控导出：支持 UTF\-8 CSV、JSON 数组两种格式。

- 输入数据流：质控合格病历、导出筛选条件、目标文件格式

- 输出数据流：清洗统计结果、标准化数据集文件流

- 接口设计

```http
# 批量执行数据清洗、字段规整
POST /api/governance/clean
# 导出标准化数据集
POST /api/export/dataset
请求体：{"format": "csv", "filters": {...}}
响应：文件流下载
```

### 7\. 词典管理

> 说明：术语归一底层支撑模块，管理员维护国标术语库，供给结构化、质控模块调用，对应需求 1\.4、2\.1、3\.4 术语归一需求
> 
> 

#### 必做 10 症状、证型、中药与方剂术语标准化

**功能描述**：将病历口语化表述映射国标标准术语，同步标注术语来源规范；术语库启动时加载进内存（导入后自动重载）
内置四大术语标准：

- 症状：《中医临床诊疗术语》GB/T 16751

- 证型：《中医病证分类与代码》GB/T 15657\-2021

- 中药：《中华人民共和国药典》2020 版

- 方剂：《中医方剂大辞典》

- 输入数据流：口语化原始术语

- 输出数据流：标准术语、规范来源文本

- 接口设计

```http
POST /api/governance/normalize
请求体：{"type": "symptom|syndrome|herb|formula", "term": "string"}
响应体：{"standardTerm": "string", "source": "..."}
```

#### 必做 16 词典管理（术语库维护）

**功能描述**：管理员专属操作，采用「LLM 即 ETL + JSON 文件即数据库 + 备份文件即版本历史」方案：上传国标术语文件，由 LLM 自动转换为 JSON 术语库（data/dictionaries/*.json）；写入前自动备份旧文件（data/dictionaries/backup/，时间戳命名），支持一键回滚到指定版本。

为术语标准化、辨证逻辑校验提供底层数据源（只读查询，无增删改后台）

- 输入数据流：国标术语文件（Excel/CSV）、回滚目标备份文件名

- 输出数据流：LLM 转换写入的 JSON 术语库文件、旧版本备份文件、导入结果摘要与失败明细

- 接口设计

```http
# 术语库导入（LLM 转换国标文件 → 写入 JSON，自动备份旧版本）
POST /api/dictionary/import
请求体：multipart/form-data 携带Excel/CSV术语文件，type区分术语类型
响应体：{"type": "symptom", "total": 1000, "imported": 980, "failed": 20, "failures": [...]}
# 术语查询（只读，供前端自动补全）
GET /api/dictionary/terms
# 版本回滚（按备份文件恢复指定版本）
POST /api/dictionary/rollback
请求体：{"type": "symptom", "backupFilename": "symptoms.json.bak_20260811_143000"}
```

### 8\. 系统管理

> 说明：系统底层基础权限、登录、审计日志能力，对应需求 4\.5 安全性、第 5 章接口需求
> 
> 

#### 必做 1 用户登录

**功能描述**：系统入口身份鉴权，固定两类角色：管理员 / 审核员，登录后按角色返回菜单列表，下发会话 Token 用于全局接口鉴权

- 输入数据流：用户名、密码

- 输出数据流：登录状态、用户角色、按角色分配的菜单列表、鉴权 Token、提示信息

- 接口设计

```http
POST /api/auth/login
请求体：{"username": "string", "password": "string"}
响应体：{"code": 200, "msg": "登录成功", "data": {"token": "string", "role": "string", "menus": ["病历管理", "结构化解析", "质控管理", "人工复核", "数据治理", "词典管理", "系统管理"]}}
```

#### 必做 2 基础权限与操作日志管理

**功能描述**

1. 固定角色方案：仅建 users 表（含 role 字段），登录成功后后端按 role 返回菜单列表，前端按菜单渲染页面，实现功能访问隔离，无需权限配置界面；

2. 操作日志：关键操作（导入、修改、删除、导出等）追加写入 logs/operation.log（格式：时间 | 操作人 | 操作内容），持久化存储，支持导出下载。

- 输入数据流：用户登录账号、密码（role 存于 users 表）

- 输出数据流：登录接口按角色返回的菜单列表、操作日志文件流

- 接口设计

```http
# 导出操作日志（读取 operation.log 文件流返回）
GET /api/logs/export
```
